### 常用命令

| 命令 | 描述 |
| :--- | :--- |
| `SET` | 设置指定 key 的值 |
| `GET` | 获取指定 key 的值 |
| GETRANGE | 返回 key 中字符串值的子字符 |
| GETSET | 将给定 key 的值设为 value ，并返回 key 的旧值 ( old value ) |
| GETBIT | 对 key 所储存的字符串值，获取指定偏移量上的位 ( bit ) |
| `MGET` | 获取所有(一个或多个)给定 key 的值 |
| SETBIT | 对 key 所储存的字符串值，设置或清除指定偏移量上的位(bit) |
| `SETEX` | 设置 key 的值为 value 同时将过期时间设为 seconds |
| `SETNX` | 只有在 key 不存在时设置 key 的值 |
| SETRANGE | 从偏移量 offset 开始用 value 覆写给定 key 所储存的字符串值 |
| STRLEN | 返回 key 所储存的字符串值的长度 |
| `MSET` | 同时设置一个或多个 key-value 对 |
| MSETNX | 同时设置一个或多个 key-value 对 |
| PSETEX | 以毫秒为单位设置 key 的生存时间 |
| `INCR` | 将 key 中储存的数字值增一 |
| INCRBY | 将 key 所储存的值加上给定的增量值 ( increment ) |
| INCRBYFLOAT | 将 key 所储存的值加上给定的浮点增量值 ( increment ) |
| `DECR` | 将 key 中储存的数字值减一 |
| DECRBY | 将 key 所储存的值减去给定的减量值 ( decrement ) |
| APPEND | 将 value 追加到 key 原来的值的末尾 |

## set 

**语法**

```
SET key value [NX | XX] [GET] [EX seconds | PX milliseconds | EXAT unix-time-seconds | PXAT unix-time-milliseconds | KEEPTTL]
```

**参数说明**

| 参数 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| key | String | 是 | 键名 |
| value | String | 是 | 值（二进制安全） |
| NX | 标志 | 否 | 仅在 key 不存在时才设置 |
| XX | 标志 | 否 | 仅在 key 存在时才设置 |
| GET | 标志 | 否 | 返回 key 的旧值 (Redis 6.2+) |
| EX | 整数 | 否 | 过期时间（秒） |
| PX | 整数 | 否 | 过期时间（毫秒） |
| EXAT | 整数 | 否 | 绝对过期时间 (Unix 时间戳，秒) |
| PXAT | 整数 | 否 | 绝对过期时间 (Unix 时间戳，毫秒) |
| KEEPTTL | 标志 | 否 | 保留 key 原有的 TTL (Redis 6.0+) |

**返回值**

| 条件 | 返回值 |
| :--- | :--- |
| 设置成功 | OK |
| NX/XX 条件不满足 | (nil) |
| 带 GET 且 key 存在 | 返回旧值；若旧值非 String 类型则报错 |

# java 客户端

## java 常用客户端

### 简介
Redis常用客户端主要有三个:

* Jedis api
    * Jedis api 在线网址 : https://tool.oschina.net/uploads/apidocs/jedis-2.1.0/redis/clients/jedis/Jedis.html
* redisson
    * redisson 官网地址 : https://redisson.org/
    * redisson github地址 : https://github.com/redisson/redisson
* lettuce
    * lettuce 官网地址 : https://lettuce.io/
    * lettuce github地址 : https://github.com/lettuce-io/lettuce-core

**在Spring boot2之后, 对redis连接的支持, 默认就采用了lettuce**

### 概念

* Jedis : 是老牌的Redis的Java实现客户端, 提供了比较全面的Redis命令的支持
* redisson : 实现了分布式和可扩展的Java数据结构
* Lettuce : 高级Redis客户端, 用于线程安全同步, 异步和响应使用, 支持集群, sentinel, 管道和编码器

### 优点

* Jedis : 比较全面的提供了Redis的操作特性
* Redisson : 促使使用者对Redis的关注分离, 提供很多分布式相关操作事务, 例如: 分布式锁, 分布式集合, 可通过Redis支持延迟队列
* Lettuce : 基于Netty框架的事件驱动的通信层, 其方法调用是异步的。Lettuce的API是线程安全的, 所以可以操作单个Lettuce连接来完成各种操作

### 可伸缩

* Jedis : 使用阻塞的I/O, 并且方法调用都是同步的, 程序流需要等到sockets处理完I/O才能执行, 不支持异步。Jedis客户端实例不是线程安全的, 所以需要通过连接池来使用Jedis
* Redisson : 基于Netty框架的事件驱动的通信层, 其方法调用是异步的。Redisson的API是线程安全的, 所以可以操作单个Redisson连接来完成各种操作
* Lettuce : 基于Netty框架的事件驱动的通信层, 其方法调用是异步的。Lettuce的API是线程安全的, 所以可以操作单个Lettuce连接来完成各种操作。Lettuce能够支持redis4, 需要java8及以上。Lettuce是基于Netty实现的与Redis进行同步和异步操作

### 比较

* Jedis :直接连接Redis Server, 非线程安全, 需使用连接池为每个Jedis实例增加物理连接

* Redisson : 基于Netty连接Redis Server, 线程安全, 功能较为简单, 不支持字符串操作, 不支持排序、事务、管道、分区等Redis特性。促使使用者对Redis的关注分离,提供很多分布式相关操作事务

* Lettuce : 基于Netty连接Redis Server, 线程安全, 一个连接实例可以满足多线程环境下的并发访问, 一个连接实例不够的情况下, 可以按需增加连接实例

### 总结

优先使用Lettuce, 如果需要分布式锁, 分布式集合等分布式的高级特性, 添加Redisson结合使用, 因为Redisson对字符串操作的支持很差

```java
package com.laolang.devstudio;

import java.util.concurrent.TimeUnit;
import lombok.SneakyThrows;
import lombok.extern.slf4j.Slf4j;
import org.assertj.core.api.Assertions;
import org.junit.jupiter.api.AfterAll;
import org.junit.jupiter.api.BeforeAll;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.TestInstance;
import redis.clients.jedis.Jedis;
import redis.clients.jedis.params.SetParams;

@Slf4j
@TestInstance(TestInstance.Lifecycle.PER_CLASS)
public class JedisSingleConnectionTest {

    Jedis jedis;

    @BeforeAll
    public void beforeAll() {
        jedis = new Jedis("192.168.56.20", 6379);
        jedis.select(0);
    }

    @AfterAll
    public void afterAll() {
        jedis.close();
    }

    @SneakyThrows
    @Test
    public void testString() {
        String msg = jedis.get("msg");
        Assertions.assertThat(msg).isNull();
        SetParams setParams = new SetParams().ex(5L);
        jedis.set("msg", "hello world", setParams);
        msg = jedis.get("msg");
        Assertions.assertThat(msg).isEqualTo("hello world");
        TimeUnit.SECONDS.sleep(6);
        msg = jedis.get("msg");
        Assertions.assertThat(msg).isNull();
    }
}
```

**RedisConfig.java**

```java
package com.laolang.devstudio.framework.redis.config;

import com.fasterxml.jackson.annotation.JsonTypeInfo;
import com.fasterxml.jackson.databind.DeserializationFeature;
import com.fasterxml.jackson.databind.ObjectMapper;
import com.google.common.collect.Maps;
import com.laolang.devstudio.framework.common.util.jackson.module.BigDecimalModule;
import com.laolang.devstudio.framework.common.util.jackson.module.Jdk8TimeModule;
import com.laolang.devstudio.framework.common.util.jackson.module.LongModule;
import com.laolang.devstudio.framework.redis.consts.CacheConsts;
import com.laolang.devstudio.framework.redis.properties.CacheDurationProperties;
import java.time.Duration;
import java.util.Map;
import javax.annotation.PostConstruct;
import lombok.RequiredArgsConstructor;
import org.apache.commons.lang3.StringUtils;
import org.springframework.cache.CacheManager;
import org.springframework.cache.annotation.EnableCaching;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.redis.cache.RedisCacheConfiguration;
import org.springframework.data.redis.cache.RedisCacheManager;
import org.springframework.data.redis.connection.RedisConnectionFactory;
import org.springframework.data.redis.core.RedisTemplate;
import org.springframework.data.redis.serializer.GenericJackson2JsonRedisSerializer;
import org.springframework.data.redis.serializer.RedisSerializationContext;
import org.springframework.data.redis.serializer.RedisSerializer;
import org.springframework.data.redis.serializer.StringRedisSerializer;

/**
 * @author laolang
 */
@RequiredArgsConstructor
@EnableCaching
@Configuration
public class RedisConfig {

    final CacheDurationProperties cacheDurationProperties;

    RedisCacheConfiguration defaultRedisCacheConfiguration;

    GenericJackson2JsonRedisSerializer genericJackson2JsonRedisSerializer;

    @PostConstruct
    public void postConstruct() {
        initGenericJackson2JsonRedisSerializer();
        initRedisCacheConfiguration();
    }

    void initGenericJackson2JsonRedisSerializer() {
        ObjectMapper objectMapper = new ObjectMapper();
        objectMapper.registerModules(new BigDecimalModule(), new LongModule(), new Jdk8TimeModule());
        objectMapper.disable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES);
        /*
         * 用于替代 objectMapper.enableDefaultTyping(ObjectMapper.DefaultTyping.NON_FINAL,
         * JsonTypeInfo.As.PROPERTY);
         */
        objectMapper.activateDefaultTyping(objectMapper.getPolymorphicTypeValidator(),
                ObjectMapper.DefaultTyping.NON_FINAL, JsonTypeInfo.As.PROPERTY);
        genericJackson2JsonRedisSerializer = new GenericJackson2JsonRedisSerializer(objectMapper);
    }

    void initRedisCacheConfiguration() {
        defaultRedisCacheConfiguration = RedisCacheConfiguration.defaultCacheConfig()
                // 默认为双冒号, 改为单冒号
                .computePrefixWith(cacheName -> cacheName + ":")
                // key 序列化为 String
                .serializeKeysWith(RedisSerializationContext.SerializationPair.fromSerializer(new StringRedisSerializer()))
                // value 使用 GenericJackson2JsonRedisSerializer 序列化为 json
                .serializeValuesWith(RedisSerializationContext.SerializationPair
                        .fromSerializer(genericJackson2JsonRedisSerializer))
                // 不缓存 null
                .disableCachingNullValues();
    }

    @Bean
    public RedisTemplate<String, Object> redisTemplate(RedisConnectionFactory connectionFactory) {
        RedisTemplate<String, Object> redisTemplate = new RedisTemplate<>();
        redisTemplate.setConnectionFactory(connectionFactory);

        // key 和 hashKey 采用 String 序列化
        redisTemplate.setKeySerializer(RedisSerializer.string());
        redisTemplate.setHashKeySerializer(RedisSerializer.string());

        // value 和 hashValue 采用 Json 序列化
        redisTemplate.setValueSerializer(genericJackson2JsonRedisSerializer);
        redisTemplate.setHashValueSerializer(genericJackson2JsonRedisSerializer);

        return redisTemplate;
    }

    @Bean
    public CacheManager cacheManager(RedisConnectionFactory redisConnectionFactory) {
        return RedisCacheManager.RedisCacheManagerBuilder
                // redis 链接工厂
                .fromConnectionFactory(redisConnectionFactory)
                // 通用缓存配置, 没有配置则默认 1 小时
                .cacheDefaults(buildDefaultRedisCacheConfiguration())
                // 配置同步修改或删除 put/evict
                .transactionAware()
                // 对于固定的 key , 可以统一配置过期时间
                // .withCacheConfiguration("xxx",CacheUtil.buildCacheConfigurationWithTtl(Duration.ofSeconds(600)))
                .withInitialCacheConfigurations(buildSpecificCacheConfigurations())
                .build();
    }

    /**
     * 默认的缓存配置对象
     */
    RedisCacheConfiguration buildDefaultRedisCacheConfiguration() {
        String cacheCommonDuration = cacheDurationProperties.getCacheCommonDuration();
        if (StringUtils.isBlank(cacheCommonDuration)) {
            return defaultRedisCacheConfiguration.entryTtl(Duration.parse(CacheConsts.CACHE_COMMON_DURATION));
        }
        return defaultRedisCacheConfiguration.entryTtl(Duration.parse(cacheCommonDuration));
    }

    /**
     * 特定的缓存过期策略
     */
    Map<String, RedisCacheConfiguration> buildSpecificCacheConfigurations() {
        Map<String, RedisCacheConfiguration> map = Maps.newHashMap();
        if (cacheDurationProperties.getCacheConfigs().isEmpty()) {
            return map;
        }
        for (Map.Entry<String, String> entry : cacheDurationProperties.getCacheConfigs().entrySet()) {
            String cacheName = entry.getKey();
            Duration ttl = Duration.parse(entry.getValue());
            map.put(cacheName, defaultRedisCacheConfiguration.entryTtl(ttl));
        }
        return map;
    }

}
```

# 缓存

## spring boot cache

### 常用注解

#### 总览

|注解|功能|
|--|--|
|`@Cacheable`|查缓存，有则返回；没有则执行方法并将结果缓存|
|`@CachePut`|执行方法后更新缓存（常用于新增或更新操作）|
|`@CacheEvict`|	清除缓存（常用于删除或刷新缓存）|

#### Cacheable

|参数|功能|备注|
|--|--|--|
|`value` / `cacheNames`|缓存组件名称, 可指定多个|如果只有一个属性，`cacheNames` 可以省略，默认使用 `value`|
|`key`|缓存 `key`, 默认使用方法的所有参数组合作为 `key`, 支持 `SPEL` 表达式|`key` 和 `keyGenerator` 是互斥的. 当同时配置时，`key` 的优先级更高，`keyGenerator` 配置将自动失效|

## 缓存与数据库一致性问题

### 原因

网络延迟, 并发读写和系统故障等, 必然导致数据不一致问题

### 方案

#### 旁路缓存模式

核心是读走缓存, 写走数据库. 

读操作: 先插 redis, 命中则返回, 未命中则查数据库, 将结果写入 redis , 然后返回

写操作: 先更新数据库, 再删除缓存. 但在高并发下会导依然会导致数据不一致问题

#### 延迟双删

执行逻辑：
1. 第一次删除 Redis 缓存
2. 更新数据库；
3. 短暂休眠（休眠时间需大于“读请求业务逻辑耗时 + 几百毫秒”）；
4. 第二次删除 Redis 缓存46。

核心优势：第二次删除可以清除在“更新数据库期间”被其他读请求意外写入的旧数据（脏数据），极大降低了数据不一致的风险45。

局限性：增加了写请求的耗时，且休眠时间的精确设定较为困难，无法保证 100% 强一致


#### 异步兜底

当数据库更新成功但缓存删除失败时，可以通过引入消息队列来保证最终一致性。
* 执行逻辑：写请求更新数据库后，向 MQ 发送一条删除缓存的消息。消费端监听该消息，执行 Redis 删除操作。如果删除失败，MQ 会触发重试机制49。
* 核心优势：将缓存删除操作与主业务流程解耦，利用 MQ 的可靠性确保缓存最终一定会被清理，避免了因网络抖动导致的永久不一致

#### binlog 订阅同步

对于架构要求极高、业务逻辑与缓存更新需要完全解耦的场景，可采用基于数据库日志的同步机制。
* 执行逻辑：业务代码只负责更新 MySQL。通过 Canal 等中间件订阅 MySQL 的 Binlog（增量日志），解析出数据的增删改操作，再通过 MQ 推送并异步更新到 Redis46。
* 核心优势：完全解耦，业务代码无需关心缓存操作；严格保证数据变更的顺序性，支持全量与增量同步。
* 局限性：架构复杂度最高，引入了额外的中间件，运维成本较大，且同步存在微小的延迟

## 缓存三大问题

### 缓存穿透

#### 定义

请求不存在数据, 即该数据既不在缓存中, 也不在数据库中, 导致大量无用请求数据

#### 方案

* 针对空数据, 添加缓存并设置一个较短的过期时间
* 前置布隆过滤器
* 前置数据校验, 例如 id 必须为正整数等

### 缓存击穿

#### 定义

某一热点 key 缓存过期瞬间, 大量并发请求同时访问该 key, 在此瞬间会有大量请求直接到数据库

#### 方案

* 分布式锁: 当缓存失效时, 值允许一个线程查询并重建缓存, 可保证一致性, 但性能差
* 逻辑过期: 设置热点数据永不过期, 但额外存储一个逻辑过期时间戳, 读取时判断是否过期，若过期则返回旧数据，同时在后台开启异步线程去更新缓存. 性能高但无法保证数据绝对一直


### 缓存雪崩

#### 定义

大量不同的 key 几种过期或 redis 服务不可用

#### 方案

* 过期时间随机化: 设置缓存过期时间时, 添加一个随机偏移量, 将请求压力分散到不同时间段
* 多级缓存: 添加本地缓存
* 利用 redis 集群提高服务可用性
* 限流与降级: 业务上添加限流和熔断降级

## RDB

RDB全称Redis Database Backup file（Redis数据备份文件），也被叫做Redis数据快照。简单来说就是把内存中的所有数据都记录到磁盘中。当Redis实例故障重启后，从磁盘读取快照文件，恢复数据。

* `save`: 由 redis 主进程执行 `RDB` , 会阻塞所有命令

* `bgsave`: 开启子进程执行 `RDB` , 避免主进程受到影响


关于配置

```ini
# 执行频率配置, 后台使用 bgsave 命令
save 900 1      # 900秒内至少有1次写操作
save 300 10     # 300秒内至少有10次写操作
save 60 10000   # 60秒内至少有10000次写操作

# 快照文件名
dbfilename dump.rdb

# rdb 文件保存目录
dir /var/lib/redis
```

## AOF

AOF全称为Append Only File（追加文件）。Redis处理的每一个写命令都会记录在AOF文件，可以看做是命令日志文件。

配置如下

```init
# 是否开启 AOF 功能, 默认关闭
appendonly yes

# AOF 文件名称
appendfilename "appendonly.aof"

# 同步方式
# 同步刷盘, 表示每执行一次写命令, 就立即记录到了 AOF 文件
# appendfsync always
# 写命令执行完先放入 AOF 缓冲区, 每隔 1 秒将数据写到 AOF 文件, 默认方案
appendfsync everysec
# 写命令执行完先放入 AOF 缓冲区, 由操作系统决定何时将缓冲区内容写回磁盘
# appendfsync everysec



# 该参数设定了触发 AOF 重写的文件体积增长率阈值，默认值为 100
auto-aof-rewrite-percentage 100
# 该参数设定了触发 AOF 重写的最小文件体积门槛，默认值为 64mb
auto-aof-rewrite-min-size 64mb
```

**重写**

AOF 文件记录的是完整的历史命令, 所谓重写就是遍历当前内存里的数据, 例如某个 key 的值经过若干次赋值, 最后是 "hello world", 那么就在新文件里只写一条 set key "hello world"


## 对比

| | RDB | AOF |
| :--- | :--- | :--- |
| 持久化方式 | 定时对整个内存做快照 | 记录每一次执行的命令 |
| 数据完整性 | 不完整，两次备份之间会丢失 | 相对完整，取决于刷盘策略 |
| 文件大小 | 会有压缩，文件体积小 | 记录命令，文件体积很大 |
| 宕机恢复速度 | 很快 | 慢 |
| 数据恢复优先级 | 低，因为数据完整性不如AOF | 高，因为数据完整性更高 |
| 系统资源占用 | 高，大量CPU和内存消耗 | 低，主要是磁盘IO资源，但AOF重写时会占用大量CPU和内存资源 |
| 使用场景 | 可以容忍数分钟的数据丢失，追求更快的启动速度 | 对数据安全性要求较高，常见 |

三个哨兵节点配置都是一样的

```
# 允许哨兵解析主机名（必须添加）
sentinel resolve-hostnames yes

# 1. 哨兵监听的端口（固定为 26379）
port 26379

# 2. 监控主节点（名称 cluster-master，IP必须是容器名，端口必须是内部6379，quorum为2）
sentinel monitor cluster-master redis-cluster-master 6379 2

# 3. 主节点密码（必须与你的 redis.conf 密码一致）
sentinel auth-pass cluster-master fcl1164891

# 4. 5秒无响应判定为主观下线
sentinel down-after-milliseconds cluster-master 5000

# 5. 故障转移超时时间
sentinel failover-timeout cluster-master 10000

# 6. 故障转移时，同时同步数据的从节点数量
sentinel parallel-syncs cluster-master 1

# 1. 允许任意 IP 访问（如果是 Docker 部署，必须加这一行，否则外部或跨容器连不上）
bind 0.0.0.0
```
